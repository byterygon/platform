# DBee acceptance databases (TSK-61)

Two throwaway PostgreSQL servers in Docker for the DBee v0.1 acceptance pass (DBee spec DOC-18
section 14) and the section 1 performance budget on a developer machine. Nothing is installed on
the host; the data lives in tmpfs inside the containers, and `down` removes everything.

CI does not use this: it keeps starting its own servers from `initdb`/`postgres` inside a network
namespace. Docker is only for the acceptance pass on a developer machine.

```sh
apps/dbee/acceptance/acceptance.sh up       # fresh servers, data loaded (about 15 s)
apps/dbee/acceptance/acceptance.sh test     # dbee-core PostgreSQL tests + dbee-server e2e against pg-tls
apps/dbee/acceptance/acceptance.sh env      # exports for the tests and the desktop driver
apps/dbee/acceptance/acceptance.sh status
apps/dbee/acceptance/acceptance.sh down     # stop, remove the containers and .state/
```

Needs Docker with Compose v2 (`docker compose` or the standalone `docker-compose`) and the image
below. The image is pinned by digest; `up` pulls it only when it is missing, so after one pull
the setup works offline.

| | |
| --- | --- |
| Image | `postgres:17@sha256:0d938e975177bef9f1f61f3f9dbcf2e0aa0a139568f66d3415ed8892eb97f6ac` (PostgreSQL 17.12, Debian 13, multi-arch index digest) |
| `pg-plain` | `127.0.0.1:55432` (`DBEE_ACC_PLAIN_PORT`), `ssl = off`: plaintext only |
| `pg-tls` | `127.0.0.1:55433` (`DBEE_ACC_TLS_PORT`), `ssl = on` with a certificate for `db.test` |

Both publish their port on 127.0.0.1 only, and DBee connects to `127.0.0.1:<port>`, never to a
container name, so the grant's address policy pins the loopback address it resolved.

**Roles.** `postgres` is trusted over TCP, as in the test clusters of `dbee-core` and the driver
(the tests use it to create their own roles). `dbee` authenticates with SCRAM; its password is
random, generated by `up` into `.state/env` (mode 600, git-ignored), and printed by `env` as
`DBEE_ACC_PASSWORD`. It is for the keychain flows (a password stored in the OS keychain and
released only to its connection).

**TLS.** `pg-tls` generates a CA and a server certificate (EC P-256, valid 7 days, name
`db.test`) with OpenSSL inside the container at first start (`initdb/15-tls.sh`). The private keys
stay in the container's tmpfs; only the CA (`.state/tls/ca.pem`), the server certificate
(`.state/tls/server.pem`) and its fingerprint (`.state/tls/fingerprint`, `sha256:<hex>` of the
DER) are copied out, for the "pinned CA file" and "pinned server certificate" policies. Use
`db.test` as the TLS server name. No key is ever committed.

**Data** (on `pg-plain`, database `postgres`):

- `public.bench_rows`, 1,000,000 x 10, the same definition as the TSK-36 benchmark
  (`crates/ambidex-bench/src/pg.rs`, `packages/ambidex/bench/README.md`), so the numbers compare
  with the Research DOC-16; the database has `synchronize_seqscans = off` as there;
- schema `wide` with 10,000 tables (`table_00001` … `table_10000`, five columns each) for the
  schema-tree budget.

**Tests against Docker.** `BYTERYGON_PG_EXTERNAL=<dir>` makes the PostgreSQL test cluster of
`dbee-core` and `dbee-server` (`apps/dbee/core/tests/support/cluster.rs`) use a running server
instead of starting one: the port, CA and fingerprint are read from `<dir>/port`, `ca.pem` and
`fingerprint`. `acceptance.sh test` recreates `pg-tls` before each test binary (the tests create
roles) and sets it to `.state/tls`.

## Performance budget on the desktop app

```sh
apps/dbee/acceptance/acceptance.sh perf [--port 55432] [--runs 3] [--out DIR] [--no-build]
```

builds `dbee-desktop` and the driver `apps/dbee/desktop/examples/acceptance` in release mode,
creates a workspace with one approved plaintext connection (through the core's
`connections.prepare` / `connections.create`) and two query tabs, then:

1. starts the real `dbee-desktop` with `DBEE_COLD_START_EXIT=1` `--runs` times (core ready,
   window ready, first page load after process start);
2. runs the driver `--runs` times. It is the same app (the `Desktop` core, the Ambidex plugin, the
   capability and CSP of `tauri.conf.json`, the bundled UI) with the TSK-39 bench hook and
   `driver.js` installed as an initialization script on the `main` window, and works through the
   UI: time to a usable window (tree and editor shown), connect and list the schemas, expand
   `wide` (10,000 tables) and its Tables group, the app's memory after 5 s idle (one connection,
   one tab), Run on `select * from bench_rows` to the first painted rows, scrolling 200 px per
   frame for 3 s from the first rows (frame intervals while the stream still ran, and after), the
   end of the stream, and Cancel on a 10M-row statement against the audit entry of the driver's
   cancel connection. It also verifies the audit chain.

Memory is the sum over the app's processes: the app, and on macOS the WebKit GPU, Networking and
WebContent services it started (`ps` RSS, and `footprint`'s physical footprint, which is what
Activity Monitor shows; RSS also counts the system frameworks every process maps); on Linux the
app and its WebKitGTK child processes (RSS).

CI runs the same measurement on Linux (job "DBee desktop budget", WebKitGTK under Xvfb) against
`local-postgres.sh`, a throwaway server from the distribution's `initdb`/`postgres` with the same
data files; it reports and fails only when a step does not work.
